reachable over Wi-Fi. No Android partition was mounted or written. The

## What the exact binaries establish

* `qca_cld3_kiwi_v2.ko` contains `wlan_hdd_pld_suspend()`; its call at
  `.text+0x43894` enters `wlan_hdd_bus_suspend()`. That function sends the
  WLAN firmware bus-suspend request through `pmo_core_psoc_bus_suspend_req()`.
  The saved Android kernel log's `kiwi_v2: __wlan_hdd_bus_suspend: bus
  suspend succeeded` line is emitted by this same module path. The PLD PCIe
  suspend wrapper dispatches the registered upper-driver suspend callback.
* In `cnss2.ko`, `cnss_pci_suspend()` calls `cnss_pci_suspend_bus()` after a
  successful upper-driver callback. The bus path requests D3hot only when
  its saved DRV-connected byte is zero. If that byte is nonzero, it skips
  `pci_clear_master()`, `pci_disable_device()`, and
  `pci_set_power_state(..., 3)` and proceeds to host link-down. The prior
  blanket D3hot description was incorrect; the exact branches are reconstructed
  in [`2026-09-20-android-pcie-binary-decomp.md`](2026-09-20-android-pcie-binary-decomp.md).
* `cnss_set_pci_link()` contains calls to
  `msm_pcie_pm_control(MSM_PCIE_DRV_SUSPEND)` and
  `msm_pcie_pm_control(MSM_PCIE_SUSPEND)`; the `cnss2.ko` relocations and
  AArch64 arguments show both enum values are possible on its link-down path.
  `MSM_PCIE_RESUME` is also used by the link-up path. Which suspend enum was
  selected depends on CNSS runtime state/firmware support; the saved Android
  receipts do not contain the corresponding `Use PCIe DRV suspend` or
  non-DRV rejection message.
* Exact `pci-msm-drv.ko` contains both `msm_pcie_drv_suspend()` and
  `msm_pcie_pm_suspend_noirq()`, the `qcom,apss-based-l1ss-sleep` property
  string, and the ICC update helper. Its APSS/L1SS noirq path is present in
  the binary and can clear the PCIe ICC request when its runtime gates pass.
  This confirms available code, not that the property or path applied to the
  active pcie0/WCN host in the captured run. The inspected public RP6 DTBO
  candidate targets `pcie1`; public RP6 source disables that host.

The exact Android endpoint-side path is now visible without rebooting into
Android. Remaining runtime uncertainty is whether the successful suspend used
the connected DRV branch (which skips explicit endpoint D3hot) or a
non-DRV route, and which host noirq/root-fixup path was selected. A D3hot
request in one driver branch does not prove that branch ran, the final
hardware state, or wake behavior.

## Limits and device safety

The A-slot modules' vermagic matches the recorded Android kernel, but static
binary contents do not prove which internal branch executed in the saved RTC
run. The exact Android source tree and merged runtime DT remain unavailable.
No device state, PCI configuration, ICC request, regulator, suspend policy,
kernel, or Android image was changed; no suspend test was run during this
inspection.
